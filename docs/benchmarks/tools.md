# Tool latency benchmarks

## Reproduce

```bash
npm run bench:tools
npm run bench:tools -- --iterations 10 --notes 1000
npm run bench:tools -- --iterations 30 --notes 100 --source /path/to/EP-097-linear-stan-map-stationarity-acceptance.md
```

Shared options:

- `--iterations N`: 1–1000 measured iterations; default 30, plus two warmups per scenario.
- `--notes N`: 1–5000 corpus notes; default 100. Each corpus note is exactly 23,688 bytes
  of synthetic Markdown with one known matching line, spread across up to ten folders.
- `--source FILE`: read-only source for the ticket-sized read/create/edit/move/delete
  payload. A normal LF Markdown H1 is preserved; actual generated byte counts are reported.
  The corpus stays synthetic, so source contents are not duplicated throughout it.
- `--temp-parent DIRECTORY`: allocate the disposable workspace on another filesystem.

Each run creates an isolated vault, an empty SDK configuration directory, and any
oversized response files beneath its scratch workspace. Everything is removed on
completion or failure. Existing notes and the source are never modified. Larger
corpora increase runtime and scratch usage: 5,000 corpus notes alone use about 113 MiB.

The lower-level `npm run bench:writes` remains available for storage, collision
allocation, and create-preview rendering. See [write measurements](writes.md).

## What is timed

The actual `registerHubbleTools` registrations are loaded into an offline Pi SDK
session. Each sample includes the compatibility argument preparer, TypeBox schema
check, bound tool execution, Vault operations, response formatting, and oversized
response persistence. The session uses the opened scratch Vault, so configuration
lookup/startup is not measured. No model prompt, credentials, or network are needed;
external extensions, skills, themes, and context files are disabled.

Fixture creation/reset, persisted-content verification, SDK startup/disposal,
workspace cleanup, UI rendering, model generation, and network latency are **not**
timed. This is a warmed handler benchmark, not end-to-end agent latency or a
cold-filesystem benchmark. Median/p95 use nearest-rank percentiles. Tests assert
correctness and report structure, not machine-dependent speed thresholds.

The byte column is the actual note payload size for note operations, 23,688 bytes
**per corpus note** for ordinary search, and the full response size for listings
and oversized matching-line search. It is not total scanned bytes or throughput.

## Scenarios

| Tool            | Workloads                                                                                                 |
| --------------- | --------------------------------------------------------------------------------------------------------- |
| `hubble_list`   | Whole vault, scoped folder, empty folder, rejected traversal                                              |
| `hubble_search` | First page, late page, scoped folder, no matches/full scan, oversized matching line, rejected empty query |
| `hubble_read`   | Ticket-sized document, 20-line window, 256 KiB truncated response, missing note                           |
| `hubble_create` | 1 KiB/ticket-sized/256 KiB Markdown, HTML, occupied exact filename                                        |
| `hubble_edit`   | Ticket-sized atomic edit, missing exact match                                                             |
| `hubble_move`   | Ticket-sized nested move, occupied destination                                                            |
| `hubble_delete` | Ticket-sized deletion, missing note                                                                       |

There are 25 scenarios: 18 successful workloads and seven expected structured
failures. The corpus and three target notes stay fixed. Mutation samples get fresh
fixtures outside the timer and are removed after verification. Edit fixtures normalize
copied body line endings to LF, avoiding mixed-LF/CRLF creation restyling; the source
itself is untouched. Move parents exist after warmup. Atomic editing retains syncing, permission preservation, conflict
checks, and atomic rename; durability is not removed to manufacture faster results.

Listings are compared with independently seeded paths. Search verifies exact
page paths, offsets, match counts, lookahead, and continuation metadata. Read
verifies exact selected contents and truncation metadata. Persisted oversized
outputs are read back in full, not merely accepted because a filename was returned.
Mutation scenarios verify exact stored content, source/destination state, and
non-overwriting behavior. Failure scenarios must preserve their expected tagged
error and leave protected notes unchanged.

## Local measurements

Environment: Node v23.11.0, macOS (`darwin`), arm64, local temporary filesystem.
Runs used the reported EP-097 file as a read-only source. It had grown to **26,985
bytes** at this measurement; the default/corpus fixture remains the original
23,688-byte size. The following tables are **milliseconds**, after the scoped-search
optimization. Runs were sequential, not competing parallel benchmarks.

## Optimization found by the benchmarks

Scoped search originally discovered **every** note before filtering to its folder.
It now resolves the folder and passes that scope into the existing secure discovery
API, so unrelated directory trees are not scanned. Root/child/path safety checks,
recursive ordering, pagination, and read failures remain in force inside the scope.
Unrelated unreadable folders no longer fail a scoped search; unscoped searches still
report those errors.

| Scoped search workload                             | Before median / p95 | After median / p95 |
| -------------------------------------------------- | ------------------: | -----------------: |
| 100-note corpus, 10-note folder                    |       7.121 / 7.903 |      3.038 / 3.622 |
| 1,000-note corpus, 100-note folder                 |     51.734 / 57.102 |    23.866 / 29.210 |
| Oversized line in 3-note folder, 1,000-note corpus |     31.462 / 34.043 |      1.795 / 2.118 |

That is approximately **2× faster** for the corpus-folder searches and **18× faster**
for the fixed three-note folder surrounded by 1,000 corpus notes. Ordinary read,
create, move, and delete were already sub-millisecond locally. Global discovery
and full/late-page searches still scale with corpus size; these results do not
claim they were optimized or explain the original agent's model/network delay.
